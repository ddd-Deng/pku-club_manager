# 引导 Agent 实现记录与对照分析

> 作者：前端组（2 人）｜日期：2026-11-10｜分支：`feature/phase2-core-frontend`
>
> 本文档记录第二阶段"用分析与设计结果引导和约束 Agent"的完整过程，
> 并与"不进行分析和设计、直接让 Agent 生成最终系统"的做法做对照。
> 对应课程要求：「引导 Agent 完成系统，对比进行分析和设计，然后用分析和设计结果
> 引导和约束 Agent，和不进行分析和设计直接产生最终系统的区别。」

---

## 1. 方法

- **版本 A（无设计直出，对照组）**：阶段二开始前，直接要求 Agent「实现两个核心功能页面」，未提供任何设计文档。产出为单文件实现的管理后台（约 890 行），已废弃，仅作对照。
- **版本 B（设计引导，本分支）**：先完成 OOA/OOD（`docs/phase2-design.md`），再据 §7「Agent 约束清单」逐条约束 Agent 实现。

## 2. 给 Agent 的核心提示词（设计约束）

实现前，我们把设计文档 §7 作为指令发给 Agent，关键条目如下：

> 1. 页面只能调用 `src/api/*` 导出的方法，禁止直接 axios / fetch / mock。
> 2. 所有请求走 `request<T>()`；mock 与真实返回信封必须一致。
> 3. `AdminConsoleView` 不得把四个分区逻辑写在一个文件里；必须拆出 `ClubProfileForm`、`ActivityManager`、`ApplicationReviewPanel`、`MemberManager` 四个子组件（放 `src/views/admin/components/`）。
> 4. 每个数据页必须有 loading / error / empty 三态，用 `StateBlock`。
> 5. 活动操作按钮按状态图渲染（draft/published/finished 策略不同）。
> 6. 样式只用 `variables.css` 变量；组件 `<style scoped>`。
> 7. 提交前 `npm run lint`、`npm run type-check` 零报错。

## 3. Agent 的澄清提问与我们的回答（人工评审过程）

| 轮次 | Agent 的问题 | 我们的决定 |
| ---- | ------------ | ---------- |
| Q1 | 管理员（admin）没有所属社团，后台应管理哪个社团？ | 组内范围决定：「管理社团」仅面向社长本人所属社团，系统管理员全局管理本阶段不做。故 `/admin` 路由守卫只放行 `clubAdmin`；社长固定操作自己所属社团（`managedClubId` 取自 `userInfo.clubId`）。 |
| Q2 | 审核通过后成员数 +1，前端要不要立即刷新？ | 是。审核成功后重新拉取申请列表与社团详情，保证视图与数据一致（顺序图 §4.2 的一致性要求）。 |
| Q3 | 活动「已结束」状态由后端定时任务维护，前端如何处理？ | 前端只读展示，不提供任何操作按钮（状态图 §5 终态只读）。 |
| Q4 | 招新帖发布表单放在哪个分区？ | 与入社申请审核同属「招新审核」分区（对应 Xmind 网页 4 的招新审核分区）。 |

## 5. 对照分析：设计引导 vs 无设计直出

| 维度 | 版本 A（无设计直出） | 版本 B（设计引导） |
| ---- | -------------------- | ------------------ |
| AdminConsoleView 结构 | 单文件约 890 行，4 个业务分区混杂，状态/加载逻辑散落 | 容器 80 行 + 4 个单一职责子组件，各自独立加载 |
| 可测试性 | 需整页挂载，无法局部验证 | 子组件可独立评审/替换 |
| 可讲解性 | 讲不清结构来源 | 类图即代码结构，逐条对应 |
| 契约一致性 | 凭 Agent 记忆对齐 api.md，字段使用随意 | 类型先行，视图严格按 types/ 取字段 |
| 需求变更成本 | 在大文件中多处定位修改 | 修改集中在单一子组件 |
| 设计模式体现 | 无意识地用了 request 适配器 | 显式识别适配器/三态/观察者模式并写进文档 |

## 6. 结论

**先有 OOA/OOD 再约束 Agent**，产出在结构清晰度、可维护性、可讲解性上显著优于无设计直出；设计文档同时成为课堂展示「人工评审过程」的直接证据。即便最终功能相同，**过程差异**正是本课程第二阶段要考察的重点——分析与设计不是形式，而是决定系统结构与可演进性的关键输入。

## 7. 第三阶段迭代案例：两个线上缺陷的定位与修复（AI 协作过程）

> 日期：2026-11-18｜对应课程要求：「以某个核心功能的开发过程为例，说明小组同 AI 协作的情况」
> 本节记录第一次迭代中两个真实缺陷的定位过程，以及由此总结的协作方法论。

### 7.1 案例 A：社团详情页出现裸露的 `<p>摄影社定期组织交流与实践活动。</p>`

**组内第一判断**：「这肯定就是多写了个 `<p>`，删掉就好。」

**AI 的定位过程**（与人的直觉不同）：

1. 全仓搜索该字符串，命中点不在前端，而在 `backend/app/seed.py`：`introduction=f"<p>{name}定期组织交流与实践活动。</p>"`。
2. 继续查契约，`docs/api.md` 4.5 明确写着 introduction 是「富文本，HTML 字符串」。
3. 再查后端写入路径，`PUT /api/clubs/{id}` 用 `bleach.clean(..., tags=["p","br","strong",...])`，**刻意保留** `<p>`。
4. 最后查前端渲染，`ClubDetailView.vue` 用 `{{ club.introduction }}` 按**纯文本**插值。

**结论**：这不是「多写了一个标签」，而是**契约、后端、前端三方对同一字段的口径不一致**（后端存 HTML，前端当纯文本渲染）。只删 seed 里的 `<p>`，社长在后台粘贴一次带格式的文本就会复发。

**人工决策点**：统一为**纯文本契约**（而不是改成 `v-html` 渲染 HTML）。理由：后台编辑用的是 `textarea`，没有任何富文本编辑器；引入 `v-html` 会带来 XSS 面且需要额外净化库，与「不新增依赖」的硬约束冲突。

**实现细节上的一次实测修正**：AI 最初打算用 `bleach.clean(tags=[], strip=True)`，实测发现两个副作用——
`R&B 社` 会变成 `R&amp;B 社`（bleach 会转义实体），而先 strip 再 unescape 又会把 `&lt;p&gt;` 还原成可见的 `<p>`。
最终采用「剥离标签 → 还原实体 → 循环至稳定（最多 3 轮）」的 `plain_text()`，实测 6 组输入全部符合预期：

| 输入 | 输出 |
| ---- | ---- |
| `<p>摄影社定期组织交流与实践活动。</p>` | `摄影社定期组织交流与实践活动。` |
| `R&B 社` | `R&B 社` |
| `<script>alert(1)</script>` | `alert(1)`（仅文本，无标签） |
| `&lt;p&gt;hi&lt;/p&gt;` | `hi` |

**修复落点（三处同时改，缺一处就会复发）**：`seed.py` 种子去掉 HTML；`PUT /api/clubs/{id}` 写入即净化；`club_data()` 读取时同样归一——第三处是为了让**共享库里已存在的脏数据**立刻显示正常，而不需要对共享库做数据订正（组内规则：不对共享库跑数据重置）。

### 7.2 案例 B：社长审核通过后，学生端看不到自己已入社

**组内讨论**：一度怀疑是「成员权限管理没刷新」或「后端没做」。

**AI 的核查顺序**（先确认已有什么，再决定写什么）：

1. 查后端：`review()` 审核通过时**已经**写入 `Member` 行、已经给学生发了 `type=application` 的通知，`link` 指向 `/profile`；`GET /api/user/applications`（3.5）也早已实现。
2. 查前端：`api/user.ts` 里 `getMyApplications()` 等方法**都已存在**，但 `ProfileView.vue` 只有一个 `PagePlaceholder` 占位——通知把人引导到一个空页面。

**结论**：后端没问题，缺口 100% 在前端。这也解释了组内「连服务器操作可以看到变化」但「学生端看不到」的分歧：数据确实变了，只是没有查看入口。

**由此产生的两处改动**：

- 实现 backlog #13 个人中心页（资料 + 改密码 / 我的入社申请 / 我的活动报名 / 活动足迹），复用既有接口，未新增后端逻辑。
- 新增契约字段 `myStatus`：`GET /api/clubs/{id}` 返回当前用户与该社团的关系（`none/pending/approved/rejected/member`）。因为学生遇到问题时的第一反应是回到**社团详情页**，而不是个人中心。该字段同时让详情页/申请页可以禁用按钮，从 UI 层抑制「反复提交」（后端本来就有 1409 兜底）。
- 按 `CLAUDE.md` 的「新增接口四步」同步：`docs/api.md` 4.4 → `types/club.ts` 的 `ClubRelation` → `api/club.ts`（无需改动）→ `mock/handlers/club.ts` 的 `relationOf()`。

### 7.3 案例 C：场地物资预约（backlog #14）的"同构实现"

AI 先探测后端是否已有相关模型（结论：`models.py` 里没有 Venue，第 6 章只有契约），然后**照抄既有代码的骨架**而不是自创范式：
`find_club(lock=True)` → `find_venue(lock=True)`；`page_result()` 分页；`fail(code, message, status)` 错误语义；审批后写 `Notification`。
时段可用性不建 slot 表，而是由 `pending/approved` 的预约单实时推导（被拒即释放时段），避免多一张需要同步的表。

### 7.4 方法论总结（课堂可讲的四条）

1. **先验契约，再改代码。** 案例 A 如果按直觉「删掉那个 `<p>`」，问题会复发；定位到"三方口径不一致"才能一次修对。AI 的价值不在于写得快，而在于**愿意把契约文档、种子数据、写入路径、渲染路径全查一遍**。
2. **先确认"已经有什么"。** 案例 B 中后端与前端 api 层其实都已就绪，若直接让 AI"实现审核同步"，很可能重复实现一遍已有逻辑。让 AI 先做存量盘点，能把工作量从"写功能"缩小到"接上入口"。
3. **约束清单要复用，风格要同构。** `CLAUDE.md` 的 7 条约束（只走 `api/*`、三态用 `StateBlock`、类型先行、mock 与真实信封一致、BEM + CSS 变量、lint/type-check 零报错）在第三阶段继续生效；后端同样要求新代码与既有 `routes/*.py` 同构。AI 产出因此能直接融进代码库，而不是"另一套风格"。
4. **计数型测试是防漂移的护栏，但要与文档同步。** 本次改动触发了两个"数量断言"失败：`len(Base.metadata.tables) == 11` → 13、`37 个核心接口` → 41。它们不是回归，而是**提醒文档与实现必须一起更新**（README、api.md、测试三处同步改），这类断言值得保留。

**未验证 / 风险**：
