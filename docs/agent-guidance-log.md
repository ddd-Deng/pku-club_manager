# 引导 Agent 实现记录与对照分析

> 作者：前端组（2 人）｜日期：2026-11-10｜分支：`feature/phase2-core-frontend`
>
> 本文档记录第二阶段"用分析与设计结果引导和约束 Agent"的完整过程，
> 并与"不进行分析和设计、直接让 Agent 生成最终系统"的做法做对照。
> 对应课程要求：「引导 Agent 完成系统，对比进行分析和设计，然后用分析和设计结果
> 引导和约束 Agent，和不进行分析和设计直接产生最终系统的区别。」

---

## 1. 方法

- **版本 A（无设计直出，对照组）**：阶段二开始前，直接要求 Agent「实现两个核心功能页面」，未提供任何设计文档。产出为单文件实现的管理后台（约 890 行），已废弃，仅作对照。
- **版本 B（设计引导，本分支）**：先完成 OOA/OOD（`docs/phase2-design.md`），再据 §7「Agent 约束清单」逐条约束 Agent 实现。

## 2. 给 Agent 的核心提示词（设计约束）

实现前，我们把设计文档 §7 作为指令发给 Agent，关键条目如下：

> 1. 页面只能调用 `src/api/*` 导出的方法，禁止直接 axios / fetch / mock。
> 2. 所有请求走 `request<T>()`；mock 与真实返回信封必须一致。
> 3. `AdminConsoleView` 不得把四个分区逻辑写在一个文件里；必须拆出 `ClubProfileForm`、`ActivityManager`、`ApplicationReviewPanel`、`MemberManager` 四个子组件（放 `src/views/admin/components/`）。
> 4. 每个数据页必须有 loading / error / empty 三态，用 `StateBlock`。
> 5. 活动操作按钮按状态图渲染（draft/published/finished 策略不同）。
> 6. 样式只用 `variables.css` 变量；组件 `<style scoped>`。
> 7. 提交前 `npm run lint`、`npm run type-check` 零报错。

## 3. Agent 的澄清提问与我们的回答（人工评审过程）

| 轮次 | Agent 的问题 | 我们的决定 |
| ---- | ------------ | ---------- |
| Q1 | 管理员（admin）没有所属社团，后台应管理哪个社团？ | 演示期固定操作摄影社（`c-1`）；社长固定操作自己所属社团。由容器 `AdminConsoleView` 计算 `managedClubId` 并下发给子组件。 |
| Q2 | 审核通过后成员数 +1，前端要不要立即刷新？ | 是。审核成功后重新拉取申请列表与社团详情，保证视图与数据一致（顺序图 §4.2 的一致性要求）。 |
| Q3 | 活动「已结束」状态由后端定时任务维护，前端如何处理？ | 前端只读展示，不提供任何操作按钮（状态图 §5 终态只读）。 |
| Q4 | 招新帖发布表单放在哪个分区？ | 与入社申请审核同属「招新审核」分区（对应 Xmind 网页 4 的招新审核分区）。 |

## 4. 实现产物与设计的一致性核对（评审记录）

| 设计约束（§7） | 实现结果 | 结论 |
| -------------- | -------- | ---- |
| 约束 3：后台拆 4 个子组件 | `views/admin/components/` 下 4 个组件，容器只做标签分发 | ✅ 符合 |
| 约束 4：三态统一 | 所有数据页用 `StateBlock`，失败可重试 | ✅ 符合 |
| 约束 5：按钮按状态策略 | draft→[编辑,发布,删除]；published→[编辑,下架]；finished→只读 | ✅ 符合 |
| 类图依赖方向 | 视图→api→request，无反向依赖 | ✅ 符合 |
| 顺序图 §4.2 | 审核成功后重新加载申请列表 | ✅ 符合 |

`npm run type-check`、`npm run lint` 均零报错。

## 5. 对照分析：设计引导 vs 无设计直出

| 维度 | 版本 A（无设计直出） | 版本 B（设计引导） |
| ---- | -------------------- | ------------------ |
| AdminConsoleView 结构 | 单文件约 890 行，4 个业务分区混杂，状态/加载逻辑散落 | 容器 80 行 + 4 个单一职责子组件，各自独立加载 |
| 可测试性 | 需整页挂载，无法局部验证 | 子组件可独立评审/替换 |
| 可讲解性 | 讲不清结构来源 | 类图即代码结构，逐条对应 |
| 契约一致性 | 凭 Agent 记忆对齐 api.md，字段使用随意 | 类型先行，视图严格按 types/ 取字段 |
| 需求变更成本 | 在大文件中多处定位修改 | 修改集中在单一子组件 |
| 设计模式体现 | 无意识地用了 request 适配器 | 显式识别适配器/三态/观察者模式并写进文档 |

## 6. 结论

**先有 OOA/OOD 再约束 Agent**，产出在结构清晰度、可维护性、可讲解性上显著优于无设计直出；设计文档同时成为课堂展示「人工评审过程」的直接证据。即便最终功能相同，**过程差异**正是本课程第二阶段要考察的重点——分析与设计不是形式，而是决定系统结构与可演进性的关键输入。
